# WAF 长轮询验收与 A/B 报告

日期：2026-09-06。Go 最终提交：`8656ecf3b2f5aeb2e82f5a377dda7888959f9e08`，已更新主仓 `gatewayCommit`。没有部署用户设备。

## 结论

两端长轮询方案通过业务回归和实际 10 分钟空闲验收。空闲控制 RPC 从 300 次降至 10 次，减少约 **96.7%**；周期性空事件领取从 300 次降至 **0 次**。1,000 条突发事件清空时间从 **3.192 秒降至 2.175 秒**，两组均实际持久化 1,003 条有效事件。

本次没有证明 Rust RSS 下降。新方案有固定连接及任务成本，采样中的 Rust RSS 略高；任务和 goroutine 数量没有随等待次数增加。CPU 数值仅代表本报告中的隔离收集进程，不能用于推算用户完整服务的 CPU/RSS 降幅。

## 实验条件

- 同一台 Apple M5、24 GiB 内存、macOS/Darwin 25.6.0 arm64；Rust 1.96.0、Go 工具链 1.26.7。
- Rust 使用 `runtime-test` 优化构建（`opt-level=z`、thin LTO），各组使用独立进程、临时 SQLite 数据库和 Go fixture，通过真实 gRPC 通信。
- 两组均使用当前客户端、生产 `EventStore` 和相同配置；旧组运行原周期调度，新组运行正式长轮询调度。这是调度算法对照，没有检出旧发行版。
- WAF 开启、聚合间隔 2 秒、每批上限 500、队列容量 1,000、事件 TTL 10 分钟。事件携带有效规则 ID，落库后用 SQLite 查询确认总数为 1,003。
- 两组并行运行；各自预热 3 秒，然后连续空闲 600 秒。之后发送 3 次单事件，每次确认完成后间隔 3 秒，再发送 1,000 条突发事件。
- 全量回归执行完成后才启动正式 A/B。每 5 秒记录 `ps`；CPU/RSS 表采用第 10–600 秒内每组每进程 118 个样本，CPU 差值窗口约 588 秒。
- 延迟定义为注入事件至队列清空且 ACK 增加，包含聚合、领取、SQLite 持久化和确认；20 ms 状态采样带来约一个采样周期的观测误差。

## 空闲结果

以下 RPC 数字均为预热结束后的增量，排除启动时立即领取。

| 指标（600 秒） | 旧周期方案 | 新长轮询方案 |
| --- | ---: | ---: |
| 空事件领取 RPC | 300 | 0 |
| 等待 RPC | 0 | 10 |
| 正常完成长等待 | 0 | 10 |
| SQLite 配置读取 | 0 | 0 |
| Rust 存活任务数 | 始终 8 | 始终 11 |
| Go goroutine 数 | 始终 7 | 始终 11 |
| 等待业务失败 / 取消 | 不适用 | 0 / 0 |

新方案的启动领取总数在整个空闲阶段保持为 1。旧组 WAF 空领取累计墙钟耗时为 193.97 ms。新组等待耗时计入独立的 `wait / waf.wait_events` 分组，不能与实际处理耗时或 CPU 相比。

新组诊断显示 9 次已完成作用域和 1 次进行中，而 Go 实际完成了 10 次等待：首个 RPC 在诊断窗口开始前已启动，不计入该窗口的作用域。这是采样边界差异。

| 隔离进程 | 旧方案 CPU 增量 / 单核等效占比 | 新方案 CPU 增量 / 单核等效占比 | 旧 RSS 中位数（范围）MiB | 新 RSS 中位数（范围）MiB |
| --- | --- | --- | --- | --- |
| Rust | 0.17 s / 约 0.029% | 0.01 s / 约 0.002% | 19.453（19.375–19.484） | 19.602（19.484–19.641） |
| Go | 0.15 s / 约 0.026% | 0.01 s / 约 0.002% | 21.789（20.859–23.766） | 21.141（20.938–21.141） |

`ps` 累计 CPU 时间的分辨率为 0.01 秒，新方案已接近测量下限。这里只能确认本次观测的空闲 CPU 开销更低，不能将单次实验的比例外推到生产。RSS 为驻留内存，包含代码页、分配器保留及采样波动；本次没有发现按等待次数持续累加的资源数量。

## 有事件结果

| 负载 | 旧方案完成延迟 | 新方案完成延迟 |
| --- | --- | --- |
| 单事件 1 | 1.784 s | 2.026 s |
| 单事件 2 | 1.000 s | 2.008 s |
| 单事件 3 | 1.009 s | 2.020 s |
| 1,000 条突发事件 | 3.192 s | 2.175 s |

旧方案首条延迟取决于轮询相位，本次零散事件到达时间刚好使旧方案更快。新方案按已确认的设计稳定聚合约 2 秒，因此不宣称所有事件延迟都下降。

突发事件两组均为 2 次有效领取、2 次 ACK。新方案只等待首次聚合，随后立即处理第二批；独立 Rust gRPC 回归也验证了第二批间隔小于 1 秒，没有额外两秒聚合等待。

负载边界资源记录如下。零散阶段合计 3 条事件，突发阶段包含此前固定的 3 秒空隙；RSS 是阶段末端值，**不是瞬时峰值**。

| 阶段 / 进程 | 旧 CPU 增量 | 新 CPU 增量 | 旧末端 RSS MiB | 新末端 RSS MiB |
| --- | ---: | ---: | ---: | ---: |
| 零散 / Rust | 0.07 s | 0.09 s | 19.984 | 20.125 |
| 零散 / Go | 0.07 s | 0.11 s | 23.922 | 22.938 |
| 突发 / Rust | 0.25 s | 0.20 s | 25.719 | 26.063 |
| 突发 / Go | 0.06 s | 0.04 s | 26.000 | 24.578 |

有事件时的 CPU 包含用于测延迟的每 20 ms 一次 HTTP 状态查询。新方案零散事件等待更久，采样次数也更多；这些数值用于完整记录实验，不能独立证明实际业务 CPU 的增减。Go goroutine 在零散和突发完成时分别仍为旧组 7、新组 11；新组停止后活动等待为 0。

## 正确性与检查

- Rust 管理端优化版完整库回归：**1,908 通过、0 失败、3 按标记忽略**，使用 4 个测试线程。本次长轮询 A/B 虽标为手动测试，已另行实际执行旧、新两组；其余忽略项是旧配置 A/B 和外部 OpenLDAP 环境测试。
- 新增覆盖：60 秒等待不受普通 100 ms 测试请求期限限制、手动领取不被长等待阻塞、停用和关机取消、相关配置调整期限、无关发布不推迟聚合、1,000 条连续分批、持久化失败释放与重试、丢失 ACK 后幂等落库、服务错误退避、网关重连、旧网关 60 秒重新探测后恢复长轮询。
- Go 全量 `go test ./...` 通过；`go test -race ./cmd/server ./pkg/waf ./pkg/admin ./pkg/proxy` 通过。覆盖已有事件、并发登记、多等待者、重新检查可领取状态、租约释放和到期、超时、取消、容量和 TTL、鉴权及参数验证。
- 审查发现并修复 Go 独立退出边界：优雅停止前取消 WAF 等待，真实 gRPC 回归验证长等待存在时仍能在 1 秒内停止，避免落入原有 15 秒强制停止期限。
- Go 生成文件重新生成后 SHA-256 一致；协议版本一致性、Rust Clippy（所有目标、警告视为错误）、Rust 格式、生产 panic 检查、任务生命周期审计通过。
- 诊断界面独立显示事件等待，五种语言检查、前端类型检查、相关 7 项测试、ESLint、源码规模检查通过。

调试版默认并发全量回归曾出现 8 项密码哈希测试的繁忙/503 失败；它们逐项复验全部通过，最终优化版全量也全部通过。没有因此放宽密码哈希限流或修改相关业务逻辑。
