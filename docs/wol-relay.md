# fnKnock 本机与跨网段 WoL 指南

运行 FnKnock 的主机可以直接唤醒自己局域网内的设备，不需要创建 Relay、配置 PSK 或开启 Relay UDP 监听。Relay 只用于目标设备位于另一个广播域的跨网段场景。

WoL Relay 是 `server-admin-rs` 的可选内置后台能力，随现有 FnKnock 服务一起启动、停止和升级。目标网段不需要安装第二个二进制、OpenWrt 插件或 systemd 服务。

内置 Relay 只接受通过 HMAC-SHA256 鉴权、时间窗校验和防重放检查的 UDP 请求，再向配置的局域网广播地址发送标准 102 字节 Magic Packet。签名 ACK 只表示广播已交给本机网络栈，不代表目标设备已经启动。

## 部署拓扑

- 本机唤醒：设备的“唤醒路径”选择“本机直接广播”，当前 `server-admin-rs` 直接发送 Magic Packet。
- 跨网段唤醒：中心端保存远端 Relay 和目标设备配置并发送签名 UDP 请求。
- 每个目标网段运行现有 FnKnock / `server-admin-rs` 实例，并在“远程唤醒 → 跨网段”中粘贴配对码。
- 中心端必须能够通过路由、端口映射或 VPN 访问边缘实例的 UDP 监听端口，默认 `40009`。
- 两端必须启用 NTP；默认允许的最大时钟偏差为 60 秒。

## 本机直接唤醒与设备发现

1. 打开“远程唤醒 → 设备”，点击主按钮“一键发现”；手工添加设备位于右侧下拉菜单中。
2. 扫描网段留空时，服务端自动枚举当前主机的直连 IPv4 网段；也可以填写一个或多个私有 IPv4 CIDR 自定义扫描范围。
3. 扫描以后台任务运行，页面每 350 ms 增量获取进度和新设备。实际响应且能从邻居表解析到 MAC 的在线设备会立即出现在列表中，无需等待整轮结束。
4. 发现结果默认不勾选，可逐台选择或使用列表顶部的“全选”。每台设备会预填一个可编辑的随机名称；名称留空时，保存时仍会自动生成。发现流程会保存对应网卡的定向广播地址，后续唤醒不经过 Relay。
5. 也可以手工添加设备。没有配置任何 Relay 时，界面会隐藏“唤醒路径”并默认使用本机直接广播。广播地址留空时，服务端会向检测到的各本机网卡广播地址及 `255.255.255.255:9` 发送。

自动模式仍将每张网卡回退到当前 `/24` 范围。自定义模式最多接受 16 个网段、合计 4096 个主机，并仅允许私有或共享局域网地址；扫描并发为 256。部分禁用 ICMP 响应的在线设备不会出现在发现结果中，仍可手工添加。Docker bridge 中看到的是容器网络；若要发现和唤醒物理 LAN，请使用合适的 host/macvlan 网络。

## 三步完成跨网段配对

1. 在控制端打开“远程唤醒 → 跨网段”，点击“添加远程网络”，只填写网络名称和目标网段 fnKnock 的可访问 IP。
2. 复制保存后显示的一段配对码。
3. 在目标网段的 fnKnock 打开同一页面，把配对码粘贴到“让其他 fnKnock 唤醒本网络设备”，点击“配对并启用”。看到“已就绪”后回到控制端测试连接。

普通用户不需要接触 Relay ID、密钥版本、PSK、监听地址、广播目标或 CIDR。系统会使用默认端口 `40009`，自动检测本机广播地址并启用接收。只有特殊 VLAN、容器网络或自定义防火墙环境才需要展开“高级设置”。

配对码包含连接凭据，应像密码一样保管。内部 PSK 由边缘实例使用 AES-256-GCM 加密保存，不进入 SQLite KV 记录、列表/详情响应、日志或普通备份。备份恢复后需要重新配对。

## 第三方平台对接

第三方平台只在已有设备的“编辑”弹窗中配置；新建设备默认不连接云平台。每台设备最多选择点灯科技或巴法云其中一个平台，服务端也会拒绝同时启用两者。非敏感配置和运行状态会随设备保存，设备密钥/私钥使用独立 AES-256-GCM AAD 域保存在本机凭据仓库中，不会出现在 API 响应、日志、事件或备份里。暂不接入会保留凭据，删除设备会一并删除凭据；恢复备份后会显示“凭据缺失”，需要重新输入。

### 巴法云

1. 先在巴法云创建 MQTT 主题，再编辑 fnKnock 中对应的 WoL 设备。
2. 启用“巴法云”，输入控制台私钥和基础主题。主题只允许字母、数字、下划线，最长 64 字符；推荐以 `001` 或 `006` 结尾以便语音平台发现。
3. 保存后 fnKnock 通过 TLS 连接 `bemfa.com:9503`，以私钥作为 MQTT Client ID 并订阅基础主题（QoS 1）。同一私钥可复用一条连接管理多个不同主题，但这些设备必须使用相同的 TLS 验证策略。
4. `on` 与 `on#...` 会走与管理端相同的冷却、Relay/本机广播、事件和在线复查链路；`off` 不会关机。在线探测明确变为在线或离线时，fnKnock 向 `{topic}/up` 发布 `on` 或 `off`，未知状态不会覆盖云端状态。

当前界面说明仅列出仍支持的小爱同学、小度、Google Assistant 和 Amazon Alexa，不再宣传已下线的天猫精灵能力。协议参考：[巴法云 MQTT](https://cloud.bemfa.com/docs/src/mqtt.html) 与 [设备类型](https://cloud.bemfa.com/docs/src/index_device.html)。

### 点灯科技 / Blinker

1. 先在 Blinker App 创建一台独立网络设备，复制设备密钥，再编辑 fnKnock 中对应的 WoL 设备。
2. 启用“点灯科技”；如需 App 按钮控制，再开启固定 `switch` 组件绑定。
3. 保存后 fnKnock 调用官方 auth API（`protocol=mqtts`）取得临时 broker、Client ID、用户名与 token，订阅 `/device/{deviceName}/r` 并向 `/device/{deviceName}/s` 回复。token 仅存在内存中；普通 MQTT 重连复用原 token，只有鉴权失效且距离上次 auth 至少 60 秒才会刷新，避免触发凭据轮换与限流。
4. fnKnock 约每 599 秒调用官方 heartbeat API。只有来源匹配的有效消息会被处理；回复限制为每秒最多一条且不超过 1024 字节。
5. `switch=on` 唤醒设备；`switch=off` 不会关机，只回复连接在线和当前探测状态；`get=state` 使用相同的状态回复。

点灯科技个人 DIY 语音助手服务已于 2025 年下线，本功能只承诺 Blinker App / MQTT 控制。协议参考：[点灯 MQTT API](https://diandeng.tech/doc/api-mqtt)、[Blinker JS SDK](https://github.com/blinker-iot/blinker-js) 和 [语音服务下线说明](https://diandeng.tech/doc/xiaoai)。

为兼容两家消费级云平台的证书链，管理界面不展示 TLS 验证选项，并默认跳过所选平台 HTTPS/MQTT 的服务端证书验证。这会降低连接对中间人攻击的防护能力；部署方应确保 fnKnock 的出口网络可信。

## 广播地址与容器网络

- 广播目标必须是 IPv4 地址和端口，每行一个；默认值 `255.255.255.255:9` 不一定适合所有网络。
- 推荐填写实际子网定向广播地址，例如 `192.168.1.255:9`。
- 多个 VLAN 或广播域可以配置多个目标，内置 Relay 会向每个目标发送同一 Magic Packet。
- Docker bridge 通常不会把容器广播透明转发到物理 LAN。容器部署需要使用合适的 host/macvlan 网络，或确保配置的定向广播地址可从容器路由到达。
- UDP 广播使用普通数据报 socket 和 `SO_BROADCAST`，不需要 `CAP_NET_RAW`。

## 防火墙与时间同步

- 仅放行中心端到边缘 `server-admin-rs` 的 Relay UDP 端口，不要误开放管理 HTTP 端口。
- `allowedSources` 是应用层预过滤，HMAC 验证仍始终执行；来源不匹配或鉴权失败的数据报会静默丢弃。
- 请求时间窗为 ±60 秒，重放缓存保留 120 秒并最多保存 4096 个 Request ID。
- 中心端使用同一签名请求最多重试三次；重复 Request ID 返回缓存 ACK，不会再次广播。

## 重新配对

在控制端点击远程网络的“重新配对”，复制新配对码并在目标网段 fnKnock 中选择“更换配对码”。新码生成后旧码立即失效。

## 故障排查

- `504`：控制端三次发送后没有收到确认，结果是“未知”。先确认目标端显示“已就绪”，再检查 UDP 路由、端口映射和防火墙。
- `clock_skew`：检查两端 NTP，不要通过扩大时间窗长期规避时钟故障。
- 页面显示监听失败：展开高级设置，检查端口是否占用、监听地址是否属于本机，以及当前部署的网络命名空间。
- Probe 成功但唤醒返回广播失败：检查广播地址、接口路由和系统是否允许 UDP 广播。
- ACK 成功但设备未启动：检查 BIOS/UEFI、网卡驱动、关机供电、VLAN 和目标 MAC。

## 抓包验收

在目标 LAN 上执行：

```sh
tcpdump -ni br-lan 'udp port 9'
```

中心端发起唤醒后，应先收到内置 Relay 的签名 ACK，抓包同时出现 102 字节 Magic Packet（6 个 `FF` 加目标 MAC 重复 16 次），最后验证目标设备能从关机状态启动。
