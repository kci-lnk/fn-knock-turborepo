# v2.4.12 → v2.4.15 上游 20005 回归调查

调查时间：2026-09-18。用户反馈降级到 v2.4.12 恢复正常；尚无故障用户的目标地址、错误详情、配置及准确时间。192.168.31.98 是同类型测试机，不是确认发生故障的机器。

## 当前结论

降级结果提高了版本相关回归的可能性，但没有确定具体提交。降级同时重启进程并清空连接池，尚需区分“旧版本确实修复”与“重启暂时清掉累积状态”；不应忽略用户的版本对照。不能以 Go 的单次连接测试通过排除 Rust，也不能把 HTTP/2 PING 告警数量当作 20005 数量。最具体的 Rust 条件性风险是证书同步事务失败后的重复服务重启；尚未证实用户满足触发条件。已补充该路径的暂停防御（见后文），未改动代理连接协议或重试策略。

20005 由 Go 的 `classifyUpstreamFailure` 产生：连接拒绝、网络/主机不可达，或临时 DNS 失败。超时、EOF、重置分别属于其他分类。Rust 自身返回 HTTP 503 不会自动变成这个错误页；Rust 停止监听本机端口、重启真正的上游、或改变上游网络条件，则可以间接触发它。

## Rust 侧候选原因

### 1. 证书同步扩展及自动恢复：有具体触发链，待现场证实

引入提交：`8b4f531b`，后续 schema 修复 `4efb83e9`。

- v2.4.12 仅选择已有证书中 `syncable` 的更新；相同证书无更新时直接返回。
- 新版还会 `adopt` 已相同的证书、创建和删除托管证书，并持久化恢复事务。
- `lifecycle/transaction.rs` 的 `apply` 和 `restore` 都调用 `refresh`；Native 实现调用 `restart_and_verify_services`，依次重启 `network_service.service` 和 `trim_nginx.service`。
- 新版启动时调用恢复，之后每 300 秒检查；**关闭 auto_sync 后仍会检查未完成事务并尝试恢复**。
- 如果恢复走到重启之后，在恢复校验阶段持续失败，事务保持未完成，下次检查会再次执行重启。前置 guard/check 失败则不会走到重启，不能将所有恢复失败都概括成重复重启。
- 原版更新和失败回滚也会重启服务；新增风险在动作范围扩大，以及跨启动、关闭自动同步后仍执行的恢复重试，而不是“v2.4.15 才首次出现 systemctl restart”。

隔离验证：提取实际 `Backend` trait 与原样 `apply/restore` 函数，使用无真实文件、数据库及 systemctl 的 Fake backend。无证书文件变更的 apply 仍调用一次 refresh；连续三次恢复校验失败调用三次 refresh。该验证证明调用顺序，不证明现场一定发生该类失败，也没有复现真实 TCP 错误。

应核对用户现场：`fnos-certificate-sync/transactions/*.json` 是否 `completed=false`、管理日志中的同步/恢复失败，以及两个 systemd 服务停止/启动的时间，是否与 20005 对齐。不要删除事务文件或备份来“消除告警”。

### 2. Rust 分配器策略：影响面较大，但没有故障证据

提交 `9f3c6818`：完整版 FPK 默认禁用 glibc tcache，mmap threshold 从 128 KiB 改为 32 KiB；原有单 arena 策略继续保留。该变化需要在真实认证/配置/终端负载下对照 CPU、延迟、内存及进程退出，不能由内存降低推出可用性不变，也不能由策略变化推出必然导致拒绝连接。

普通处理变慢更接近 timeout；要解释 20005，仍需证明后台退出、监听缺失，或其他实际 connect/DNS 失败。当前测试机直连无异常。后续已补做正式 Rust 制品与分配器组合的隔离 A/B，见文末；该合成负载不能替代故障用户真实场景。

### 3. 已检查但暂无直接 20005 机制的变更

- Rust 主监听器、服务任务生命周期和主要 Go 配置同步逻辑在该发布区间未更换；runtime_health 的发布区间改动主要是 Windows/NetBSD 兼容，不能拿发布后的 `9d2d8c17` 倒推 v2.4.15 原始回归。
- 高级认证迁移会删除损坏配置、恢复先前隔离的站点；错误配置可影响认证/路由，但未发现其改变上游 URL 或关闭 Rust 监听器的证据。
- FN Connect 清理主要在启停/升级时运行；Rust reconciler 改动加强了配置读取和规则写入的串行化，尚未找到造成常规上游间歇拒绝连接的路径。
- 新终端资源采样按需启动、有超时和独立子进程组，不是所有访问都会触发。仍应结合用户是否打开终端判断负载影响。
- Cloudflare 入口身份校验失败走 400，隧道断开本身也不等同于网关已经返回的 20005。

## 后续防御性修复（尚未部署）

- 在证书变更/恢复前持久化暂停标记，操作成功才清除。故障、回滚报错、进程中断后，后台定时器、通知以及后续启动均不自动重复变更服务。旧版本留下的未完成事务允许首次自动恢复；该次失败后也会暂停。
- 手动恢复通过原同步 API 的 `recovery_only=true` 执行，不能与 action_ids/snapshot_version/target_ids 混用；不执行新同步动作。成功后解除暂停，并按原配置恢复后续自动同步。失败保留事务、备份和暂停标记。
- 页面在预览不可用时仍提供恢复入口，说明可能短暂中断飞牛访问；自动同步开关不能绕过暂停保护。
- systemctl restart/is-active 客户端调用增加等待上限；服务刷新开始/结束记录共同 operation_id、服务名称、耗时和结果，暂停事件进入运行诊断日志。超时停止等待并不保证 systemd 已取消后台作业，因此仍需要事务恢复和暂停保护。
- 未修改 HTTP/2、分配器、自动重试或实际代理路由。该修复针对已确认的重复重启风险，不代表已确认用户 20005 的唯一根因。

| --- | --- | --- |

| 鉴权域名 `/api/auth/bootstrap` | 客户端等待 7 秒后超时 | HTTP 503，connect_unavailable，页面 **20005** |

### 以 Rust 鉴权稳定性为主线的追加审计

#### 进程失效面与版本范围

- 正式 release 的 `panic = "abort"` 在 v2.4.12 已存在。HTTP 鉴权、RPC、后台管理、终端、证书等共用 Rust 进程；任意线程 panic 可关闭整个进程及 AuthPort，不能只搜索 auth 目录。请求任务的 JoinError 处理无法兜底 abort 模式。
- `app.rs`、`app/server.rs` 在正式 v2.4.12→v2.4.15 无变更，启动后没有看到新增“定时重建鉴权监听”逻辑。监听共用取消令牌；启动/停止和主服务失败传播仍是既有实现。
- fnOS 启动脚本启动 Rust 后返回，脚本本身不持续 wait/restart 管理进程；status 检查进程存在。外部应用中心是否另行自动拉起不由此脚本证明。崩溃后可出现 Go 仍在但鉴权端口消失的窗口。
- 机器正式实例的 management-crash.log 有 470 字节旧记录：2026-08-28、v2.3.6、row.rs:89、index out of bounds。对应终端宽字符修复 36c16a86 在 v2.4.12 之前，不能拿该历史记录归因本次回归。本轮未发现新的 panic 记录；没有记录也不能排除 OOM、SIGKILL 或原生库崩溃。
- 新版仍需关注的条件路径：高级鉴权安全豁免查询（需要高级策略与对应安全检查启用，单有 cookie 不足以覆盖）、新增终端指标收集、证书同步恢复，以及 rustls/aws-lc 依赖升级。普通匿名 HTTP 压测不能覆盖 SSH/OIDC/SMTP 等各自依赖路径，也不能证明原生加密库无问题。目前未发现这些路径导致进程退出的可复现证据。

日志出现 `failed to store HMAC nonce`、`database is locked`，代码位于 `auth/hmac.rs` 的 `set_nonce_if_not_exists`。这说明内部签名 HTTP 入口需要主 SQLite 写入；独立 auth reader 无法消除所有鉴权对主写队列的依赖。该 HMAC 路径不是两版本之间新增的。未来改进应保持防重放语义，对入口排队设置有界等待/容量，失败关闭鉴权并返回可区分的暂时不可用状态；不能跳过 nonce 校验或直接无鉴权放行。

监控盲点：`runtime_health.rs` 的 management 探测在循环内构造 running，auth_bridge 依赖 Go 的 bridge serving 状态；都不是独立 AuthPort 的端到端 HTTP 成功证明。后续应由 Go/独立观察者关联 Rust PID/starttime、AuthPort TCP/HTTP、bridge 请求延迟、SQLite 排队、退出状态与 20005 时刻。优先补这些区分证据，避免无条件自动重启掩盖原因。

正常负载重复组：v2.4.12 为 10190 次（7649×200、2541×302），v2.4.15 为 8928 次（6696×200、2232×302），均无异常，最终 FD=90、RSS 约 36.6 MiB。两轮新版吞吐较低、P99 较高（重复组 447ms 对 351ms），这是值得后续按接口拆分的性能线索，不应当成进程退出的证据或忽略不计。实验按旧后新顺序、只有两轮，无随机顺序与 CPU 归因，尚不能判定来源。两版四个正常组共 37624 次请求，2 次 503、0 次 20005、0 次进程退出。

脚本与原始 JSON：`auth-pressure.py`、`auth-pressure-repeat.py`、`auth-pressure-unthrottled-{2412,2415}.json`、`auth-pressure-repeat-{2412,2415}.json`，均在实验目录。运行方式与 auth-failure.py 相同，改 Python 文件名即可；保留已有运行目录时需修改 label。

### 2026-09-19 防御性改进（工作区实现，未部署）

按最终确认保留 HMAC 和 nonce 防重放机制，HTTP HMAC nonce 改用 AppState 共享的进程内存表，不再写 SQLite。固定最多 131072 条，保存定长 SHA-256 指纹而非原始 nonce；nonce 输入限制 8–128 字节。HashSet 去重与按插入顺序的过期队列在同一短锁内原子更新，重复请求不刷新寿命；单调时钟 TTL 为 600001ms，覆盖原有时间戳正负五分钟的完整窗口边界，访问时清理过期项。

用户明确要求容量满也接纳新请求：因此满表淘汰最早记录，再插入新 nonce，不返回容量满错误。**这是明确的可用性取舍：提前淘汰的 nonce 或进程重启丢失的 nonce，不再有完整时间窗口内的防重放保证；签名、请求方法/URI/正文绑定和时间戳校验仍然必须通过。** 无效签名不占表；仅请求在有效内存记录中重放才拒绝。没有新增后台任务、数据库写入或原始 nonce 日志。验证码消费 nonce 的持久化语义保持原实现，未误删其一次性使用保护。

HMAC 错误翻译改读已有内存 locale，避免错误响应重新排入 SQLite 队列；时间戳差使用 abs_diff 防止极端输入整数溢出，并在正文读取后再检查一次有效期。集成测试持有 SQLite BEGIN IMMEDIATE 写锁，验证无效签名拒绝、有效签名放行和重复 nonce 拒绝均在 500ms 测试截止内完成，且 nonce 没有落库。

其他改进：
- Rust 登录 HTML 模板在启动时载入，最大 1MiB，避免每次登录页面请求的文件读取；继续按挂载路径渲染 base，保持 no-store 和 HEAD 行为。文件更新需要随应用正常重启，符合打包静态资源生命周期。
- Go 使用独立复用的鉴权连接池，等待响应头最多 30 秒；覆盖内置 `/__auth__/` 及鉴权域名中指向本机 AuthPort 的映射。普通业务上游与响应正文流不应用该新超时。
- 内置鉴权代理补齐安全的 upstream_failure 诊断、错误分类与不缓存响应，区分超时、拒绝连接等；记录 route_type=auth_proxy，沿用日志限流、轮转和脱敏，不记录签名、nonce、请求正文。

这些改进消除已确认的耦合并改善故障可诊断性，不代表已证明 v2.4.15 进程退出的唯一根因。Go 改动仍在相邻仓库工作区，正式制品需要包含该 Go 版本才会获得超时和诊断改进。

验证结果：Rust 全量库测试 2052 通过、8 忽略；最后的边界与模板缓存测试补充后，HMAC/static_files 专项 44 通过。`cargo clippy --lib -- -D warnings`、生产 panic guard、后台任务生命周期审计通过。Go `go test ./...` 通过，proxy/logger race 测试通过；新增测试覆盖独立连接池、业务超时不变、鉴权上游停止/卡住时的错误分类，以及 auth_proxy 脱敏诊断落盘。两仓库 diff 检查通过。本轮仅修改和本地验证，没有替换设备二进制或重启生产服务。

### 2026-09-19 追加审计与修复

审计当前 Rust/Go 工作区后修复三处边界：

1. nonce 计时原在获得互斥锁之前采样；调用方若被长时间延迟，会缩短新记录的实际保留时间。改为持锁后采样时钟，以原子入表时刻计算保留期，并补充受阻调用的计时测试。容量、先进先出淘汰和已明确接受的重放取舍不变。
2. 证书暂停标记及待恢复日志的新增检查使用同步文件 API，却有调用位于 Tokio 异步任务中。将定时检查、失败记录及详情查询的相关磁盘读取移入 await 的 spawn_blocking 工作；详情查询继续在异步锁下串行化，并在读取/工作线程失败时保守标记需要恢复。避免慢 NAS 文件系统直接占用鉴权共用的异步执行线程。
3. Go 本机鉴权目标判定只识别数字回环地址，遗漏 `localhost`。补充大小写不敏感的精确 localhost 匹配，继续校验协议与 AuthPort；测试确认 localhost.example.com 等普通域名不被误判。
