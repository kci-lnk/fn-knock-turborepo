# Rust 运行诊断

管理界面进入 **事件中心 → 状态 → 运行诊断**，打开“Rust 运行诊断”窗口。这里观察当前 Rust 管理进程，不包含 Go 网关或其它 fn-knock 实例的资源占用。

## 采集与导出

1. 点击“开始 60 秒采样”。服务端按每秒一次采集进程资源，并开启后台任务与 SQLite 操作统计；打开窗口本身不会启动采集。
2. 等待自动结束，或点击“停止并保留结果”。关闭窗口只停止浏览器轮询，已启动的服务端采集仍会自动结束。
3. 点击“采集内存详情”，按需读取当前内存组成。它不会调用内存回收，与 60 秒采样分别记录时间。
4. 导出窗口内的 JSON，保留逐秒样本、操作统计和内存详情。状态页原有的诊断导出也会包含当前运行诊断报告。

同一管理进程只保留最新一轮采集；正在采集时再次开始会复用当前轮次，结束后重新开始会替换上次结果。内存详情保留最近一次独立快照。服务重启后这些内存中的结果消失，应先导出再重启。

## 指标口径

| 指标                    | 含义与限制                                                                                                                                                                               |
| ----------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| CPU                     | 一个逻辑核满载为 100%，多核并行可超过 100%。使用相邻样本的 CPU 时间差计算；首个样本没有基线，值为 `null`，不能当作 0%。读取失败后也会重新建立基线。                                      |
| RSS、匿名内存、文件映射 | RSS 是当前驻留内存；匿名内存可能包含堆、栈和匿名映射，不能等同于泄漏。文件映射驻留与匿名分配需分别比较。数值单位在 API 中为字节。                                                        |
| 分配器统计              | glibc 的账目，不等于精确的 Rust 存活对象大小。`free_bytes` 不保证全部驻留或可归还系统，`releasable_bytes` 也只是分配器估计。                                                             |
| 累计/最长 wall 时间     | 操作从开始到完成的经过时间。异步任务包含等待网关、锁或 I/O 的时间，不能用 wall 时间当 CPU 时间；任务与其内部 SQLite 操作还会重叠，不能相加当进程总耗时。                                 |
| SQLite CPU 时间         | 仅在实际 SQLite 工作线程闭包内开始、结束测量；不含提交前的异步 admission 排队。覆盖 primary、analytics、auth-read 和 health 连接；不是整个 Rust 进程的 CPU 剖析。平台不支持时为 `null`。 |
| 次数、失败、取消        | `calls` 是已结束的 scope 数，包括失败和取消；`failures` 表示显式错误，`cancelled` 表示 scope 未正常结束。HTTP 取消后已经提交的 SQLite 工作仍可能执行完成，统计的是实际执行结果。         |
| `in_flight`             | 正在运行，或采集停止时尚未结束的操作数。停止会冻结统计；这些操作后来完成也不会补入本轮，不能据此认定卡死。                                                                               |
| `rows`                  | 插桩主动上报的条目数，可为空，不保证是数据库受影响行数。例如 `traffic.collect` 上报观察到的流量快照记录数。                                                                              |
| primary 队列            | 当前排队数和活动操作时间有助于判断等待。报告中的队列峰值等累计字段属于连接生命周期，开始新一轮采集不会重置它们。                                                                         |

异步任务目前覆盖 `traffic.collect`、`waf.drain_events` 和 `auth_mobility.maintenance`。SQLite 默认使用编译期操作类型名称，不包含 SQL 文本、键值或配置参数。两条流量 pipeline 额外使用明确名称，便于区分 CPU 来源：

- `traffic.snapshot.persist`：写入流量增量快照的事务，包括该次写入附带的旧点裁剪。
- `traffic.retention.prune`：保留期清理的批量旧点删除事务；后续空序列清理仍以其自身方法名称单独统计。

只统计采集开启后开始的操作，之前已经运行的长操作不会补录；采集结束后也不会补齐尚未完成的操作。这些记录只能缩小热点范围，不能直接给出未插桩函数的调用栈或对象分配来源。采集会产生时钟读取、统计锁、进程信息读取和报告序列化开销，应在双方都启用相同采集方式时比较。

## 如何比较两台设备

1. 记录版本、CPU 型号、逻辑核数、PID、运行时长及启用的功能；尽可能确认二进制一致。不同 CPU 的同一百分比不代表相同工作量。
2. 先各采一轮相同空闲条件的数据：保持相同管理页面与访问方式，暂停人为压测，记录仍在进行的实际网关访问、扫描或备份。
3. 再在双方重复同一种操作、访问频率和并发数，各采完整 60 秒。每轮结束后用相同方式刷新内存详情并导出，避免一方持续刷新其它页面而另一方完全空闲。
4. 对比逐秒脉冲、SQLite 各标签 CPU、任务 wall/条目数及排队情况。结果有读取错误、截断或采样缺口时，应保留这些信息，不能把缺失值当作零。
5. 怀疑内存增长时，重复“相同操作 → 相同空闲时间 → 采集”的循环，并核对同一个 PID。一次较高 RSS、分配器空闲空间或短时间 RSS 稳定，都不足以单独确认或排除泄漏；不能把重启前后的不同进程串成增长曲线。

## 平台与资源边界

| 平台               | 可用范围                                                                                                             |
| ------------------ | -------------------------------------------------------------------------------------------------------------------- |
| Linux              | 进程与线程 CPU、RSS/匿名/文件映射/交换空间、`smaps` 汇总；具体字段以当前内核读取结果为准。                           |
| Linux + glibc      | 运行时存在 `mallinfo2` 时提供分配器统计；旧 glibc 缺少该符号时返回不可用，不要求升级。musl 不提供这组统计。          |
| macOS              | 进程 CPU 与 RSS；当前不提供线程 CPU、Linux 内存映射分类或分配器详情。                                                |
| Windows / 其它平台 | Windows 可读取进程工作集；当前无进程/线程 CPU 采样及上述内存分类。其它平台按实现返回不可用字段，不能把 `null` 当零。 |

每轮目标时长 60 秒，最多保存 61 个样本；错过的采样周期会跳过，不追补密集读取。Linux 每次最多检查 256 个线程，保存 CPU 前 8 项；内存详情最多读取 2 MiB `smaps`、解析 4096 个映射并保留前 8 个匿名区域。操作统计最多 128 个不同静态标签，每个标签最多 200 个字符，超出数量记入 `dropped_operations`。

资源采样跨轮次最多一个阻塞读取，内存详情最多一个阻塞读取且完成后有 3 秒刷新间隔。浏览器取消不会提前释放实际读取持有的许可。采集停止或开始新轮次后，旧操作的完成结果不会补入已停止或新一轮统计。报告只导出受限指标、固定线程分类和静态操作标签，不读取地址空间内容，不包含原始内存地址、映射路径、SQL 参数、请求内容或环境变量。

## 管理 API

四个接口均返回现有成功响应封装中的 `RuntimeDebugReportData`，沿用当前部署模式的管理入口认证和代理限制，不属于公开路径白名单，也不新增认证令牌。应通过现有管理入口与管理会话访问。

| 方法与路径                                       | 行为                                                     |
| ------------------------------------------------ | -------------------------------------------------------- |
| `GET /api/admin/runtime-health/debug`            | 读取当前报告，不启动采集、不扫描数据库。                 |
| `POST /api/admin/runtime-health/debug/capture`   | 开始 60 秒采集；已有运行轮次时复用它。                   |
| `DELETE /api/admin/runtime-health/debug/capture` | 停止并保留当前结果。                                     |
| `POST /api/admin/runtime-health/debug/memory`    | 按需刷新内存详情；读取忙或处于刷新间隔内时返回当前报告。 |

开发入口为 [`runtime_health/debug.rs`](../apps/server-admin-rs/src/runtime_health/debug.rs)、[`debug_resources.rs`](../apps/server-admin-rs/src/runtime_health/debug_resources.rs) 和 [`operations.rs`](../apps/server-admin-rs/src/runtime_health/operations.rs)。变更字段或路由后按 [API 契约说明](../packages/api-contract/README.md) 更新生成文件。

构建后可运行 `npm run runtime:debug:e2e`，使用隔离的临时运行环境验证登录保护、页面入口、真实 60 秒自动结束、停止冻结、内存采集、导出与窄屏布局。可通过 `FN_KNOCK_RUNTIME_SERVER_BIN` 和 `FN_KNOCK_RUNTIME_E2E_GATEWAY_BIN` 指定本地测试二进制，通过 `FN_KNOCK_RUNTIME_DEBUG_E2E_OUTPUT_DIR` 指定报告与截图目录。
