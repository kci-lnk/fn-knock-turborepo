## 已排除的简单解释

- `/proc/<pid>/stat`的utime+stime按本机CLK_TCK=100换算。基线每窗口3.14–3.63 CPU秒（314–363 tick），候选8.29–8.62秒（829–862 tick）。一个tick均摊约0.0013/0.0008ms每请求，远小于观察差；数个tick误差不能解释幅度。
- 请求窗口约60.03–60.08秒，时长差不能解释该变化。20秒预热也六对同向，配对中位约+41.10%；预热没有周期health采样，故不能只归因于正式测量中的health轮询。
- Go平均占用约0.058→0.139核。相同固定每秒后台成本在更高吞吐下应被摊薄，本身不能解释CPU/request上升；但目前并未证明两版本后台成本相同。

## 静态检查与归因限制

92d4c0c→4d15fa3的TTL0正常路径仍是一次 `AuthorizeHTTP(PREFLIGHT_AND_VERIFY)`，不启用singleflight；惰性protobuf在首次需要时构造一次。302分支直接返回，不进入业务反代的捕获、上游Cookie或Trailer处理。本轮 `pkg/rpcbridge` 产品代码无变化。

这仅排除代码上明显多一次RPC或业务反代的解释，不证明实际RPC数量、响应字节或调度行为完全相同。计数覆盖整个Go进程，含后台、管理请求和系统态时间，CPU快照窗口也略宽于请求窗口。两端同时升级且实际吞吐不同，当前没有该路由Go CPU profile，不能区分Go代码、跨进程交互/调度及负载相关后台工作。后续若继续定位，应独立采集该路由的Go CPU profile/RPC计数，并控制实际请求率；本轮不凭猜测修改产品。
